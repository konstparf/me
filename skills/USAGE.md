# Как пользоваться библиотекой в работе

Скиллы – это не документация «на почитать», а рабочие инструкции, которые подключаются к ИИ-агенту под конкретную задачу. Ниже – как это делать так, чтобы они реально экономили время и повышали качество.

## 1. Три способа подключения

### Claude Code (терминал, работа с файлами и кодом)

Лучший вариант для кода, прототипов и длинных документов в репозитории.

```bash
git clone https://github.com/konstparf/me.git
mkdir -p ~/.claude/skills
cp -r me/skills/0*/* ~/.claude/skills/
```

После этого Claude сам подхватывает нужный скилл по описанию задачи. Можно и явно: «используй скилл spec-review».

Для отдельного проекта скиллы кладутся в `.claude/skills/` внутри проекта – тогда они едут вместе с репозиторием.

### claude.ai (чат)

- Отдельный скилл: заархивировать его папку (например, `cjm/`) и загрузить в настройках в разделе навыков.
- Или проект: положить в знания проекта `working-principles`, `skill-router` и 3–5 скиллов под тему проекта (например, для ТЗ – `requirements-spec`, `user-stories`, `spec-review`, `process-modeling`).

### Свой бот или агент (idea-check, DeepSeek и др.)

1. Системный промпт всегда содержит `working-principles` и файл контекста компании (см. раздел 3).
2. Первый вызов модели: `skill-router` + запрос пользователя → модель возвращает список нужных скиллов.
3. Второй вызов: подгрузить выбранные `SKILL.md` и выполнить задачу.
4. Для вычитки – третий вызов в «чистом» контексте: только результат + `spec-review` или `code-review`. Так проверка независима от автора.

Подключать все 37 файлов сразу не нужно: контекст раздуется, а качество упадёт.

Чтобы в боте не дублировать файлы, можно подключить библиотеку как подмодуль: `git submodule add https://github.com/konstparf/me.git vendor/me` и читать файлы из `vendor/me/skills/`.

## 2. Типовые сценарии

| Ситуация | Что сказать агенту | Скиллы |
|---|---|---|
| Пришла идея или запрос от заказчика | «Разбери идею: <текст>. Контекст компании – в context.md» | `idea-triage` → `hypotheses` |
| Нужно понять, как это делают другие | «Исследуй, как крупные компании решают <задачу>, сравни коробки и свою разработку» | `desk-research` → `fact-check` |
| Провёл интервью | «Вот заметки 6 интервью. Сделай синтез и JTBD» | `research-synthesis` → `jtbd` |
| Нужно увидеть путь сотрудника | «Построй CJM для <роль> в сценарии <…> по этим данным» | `cjm` → `service-blueprint` |
| Процесс запутан | «Опиши AS-IS по этим регламентам и заметкам, найди потери, предложи TO-BE без автоматизации и с ней» | `process-modeling` |
| Нужен прототип | «Сделай кликабельный HTML-прототип сценария <…> на реалистичных данных» | `user-flows-ia` → `prototyping` → `ui-design` |
| Прототип CRM, реестра, рабочего места HR | «Сделай прототип рабочего места <роль>: список, карточка, согласования» | `user-flows-ia` → `prototyping` → `complex-ui` → `ux-review` |
| Готовлю ТЗ для разработки | «Собери требования, потом отдельно вычитай их» | `requirements-spec` → `user-stories` → `spec-review` |
| Пишу код (бот, пет-проект) | «Составь план по спеке, потом делай по задачам с тестами» | `implementation-plan` → `coding-workflow` |
| Перед релизом | «Проверь безопасность изменений, отчёт по формату» | `security-review` + `code-review` |
| Нужно согласование руководства | «Посчитай эффект с тремя сценариями, потом подготовь одностраничник и ответы на возражения» | `business-case` → `decision-defense` |
| Сервис запущен, а им не пользуются | «Вот метрики и обращения. Что мешает внедрению?» | `launch-and-adoption` |

## 3. Файл контекста компании

Большая часть ошибок агента – из-за незнания контекста. Заведи на каждую компанию (или вымышленный пример для демонстраций) файл и подкладывай его в каждую задачу:

```markdown
# Контекст: <компания>
- Размер и структура: … сотрудников, … юрлиц, филиалы, производство / офис
- Размещение: облако разрешено / только on-premise
- ИБ и ПДн: что можно отдавать во внешние сервисы, кто согласует
- Системы: кадровый учёт (ЗУП/SAP/…), SSO, портал, ЭДО, трекер
- Зрелость: что уже автоматизировано, есть ли своя разработка
- Стейкхолдеры: кто принимает решения, кто влияет
- Ограничения: бюджет, сроки, регуляторика, импортозамещение
- Принятые термины: как здесь называют сотрудников, заявки, подразделения
- Редполитика: обращение по умолчанию (вы / ты в каких сервисах), ссылка на глоссарий, исключения – по шаблону из `editorial-policy`
```

## 4. Правила, без которых скиллы работают хуже

1. **Человек – на воротах.** Агент готовит, вы решаете: после разбора идеи, после требований, перед кодом, перед релизом. Не пропускайте шаг согласования, даже когда результат выглядит гладким.
2. **Проверка – отдельным проходом.** Автор плохо находит свои ошибки, и агент тоже. Вычитку требований, ревью кода и безопасности делайте в новой сессии, давая только результат и нужный скилл.
3. **Не весь конвейер каждый раз.** Маленькая задача – 1–2 скилла. Полный путь – только для крупной инициативы.
4. **Требуйте `OPEN`, а не догадки.** Если в результате нет ни одного открытого вопроса по сложной теме – скорее всего, агент что-то выдумал. Спросите: «Что здесь допущение, а что факт?»
5. **Артефакты храните рядом с кодом и друг с другом.** Проблема, JTBD, CJM, требования, ADR – в папке проекта в git. Тогда следующий шаг агент делает с учётом предыдущих, а вы видите историю решений.
6. **Персональные и конфиденциальные данные.** Не загружайте во внешние ИИ-сервисы реальные выгрузки с ПДн, зарплатами, оценками и внутренние документы без согласования с ИБ. Обезличивайте или используйте вымышленные данные.

## 5. Как развивать библиотеку

- **После каждого применения** – одна строка в заметки: где агент ошибся или что пришлось поправлять руками. Раз в неделю-две превращайте это в правку скилла (правило, пример или анти-паттерн под эту ошибку).
- **Каждая правка – отдельный коммит** с пояснением, на каком случае улучшено. Для крупных изменений – ветка и pull request, чтобы видеть разницу.
- **Новый скилл** – только когда одна и та же работа повторилась 2–3 раза. Пишите по `skill-writing`, проверяйте на 3–5 реальных задачах «без скилла и со скиллом».
- **Проверка на другой модели.** Если пользуетесь и Claude, и DeepSeek в боте – прогоняйте важные скиллы на обеих: модели по-разному понимают одни и те же инструкции.
- **Сверка с masterspec.** Для крупных систем с командой аналитиков полезно перейти на полный [masterspec](https://github.com/deminded/masterspec) – эта библиотека совместима с ним по духу (OPEN, «что/как», вычитка по осям), и переход не потребует ломать привычки.

## 6. Что даёт библиотека кроме экономии времени

- **Единое качество артефактов** – у ТЗ, CJM и бизнес-кейсов одинаковая структура, их проще сравнивать и согласовывать.
- **Онбординг** – новый аналитик или продакт получает не «спроси у меня», а готовый способ работы.
- **Витрина подхода** – ссылка на библиотеку показывает, как вы работаете: от проверки потребности до внедрения. Её можно давать в портфолио и обсуждать на собеседованиях.
