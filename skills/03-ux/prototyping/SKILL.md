# Прототипирование

Цель – сделать самый дешёвый прототип, который отвечает на конкретный вопрос.

## Шаг 1. Что проверяем

| Вопрос | Детализация | Форма |
|---|---|---|
| Правильная ли структура и последовательность шагов? | Низкая | Схема флоу, бумажные эскизы, вайрфреймы |
| Поймут ли люди, как выполнить задачу? | Средняя | Кликабельный прототип на реалистичных данных |
| Нравится ли внешний вид, соответствует ли бренду? | Высокая | Макеты в дизайн-системе |
| Убедит ли решение руководство? | Средняя-высокая | Демо-прототип с историей одного пользователя |
| Реализуемо ли технически? | Не про интерфейс | Технический спайк |

Не делай высокую детализацию для проверки структуры: люди начнут обсуждать цвет кнопок.

## Шаг 2. Параллельные концепции

Для новых решений сделай 2–3 разные концепции, а не одну. Показывай пользователям несколько – они легче критикуют, когда есть с чем сравнить, и меньше стараются быть вежливыми.

## Шаг 3. Вайрфрейм-спецификация (перед рисованием)

Для каждого экрана:

```markdown
### Экран: <название>
Задача пользователя на экране: …
Откуда приходит / куда уходит: …
Блоки (по приоритету сверху вниз):
1. <блок> – что показывает, какие данные, откуда
2. …
Основное действие: … (одно)
Второстепенные действия: …
Состояния: пустое / загрузка / ошибка / нет прав / успех – что показываем в каждом
Тексты: заголовок, подсказки, сообщения (см. ux-writing)
```

## Шаг 4. Кликабельный HTML-прототип

Когда прототип делает ИИ-агент:
- Один HTML-файл, без сборки, открывается в браузере. Данные – в JS-объекте в начале файла.
- **Реалистичные данные:** живые ФИО, должности, даты, длинные названия подразделений, крайние случаи (0 дней отпуска, 15 подчинённых, очень длинное имя). Lorem ipsum скрывает проблемы.
- Покрывает основной сценарий целиком и 1–2 ключевые ошибки.
- Состояния переключаются (например, параметром в URL или скрытой панелью для ведущего теста).
- Адаптив: проверь на ширине телефона, если пользователи могут быть на мобильном.
- Без настоящих персональных данных и без реальных интеграций.
- Для рабочих интерфейсов (CRM, реестры, согласования) – объёмы данных, переключатели и заготовки экранов из `complex-ui`.
- Простая визуальная основа: системный шрифт, нейтральные цвета, один акцентный цвет для основного действия. Если есть дизайн-система компании – используй её токены.

## Шаг 5. Подготовка к проверке

- Сценарии задач для теста (см. `usability-testing`).
- Что считаем успехом прототипа.
- Список того, что прототип **не** показывает, чтобы не вводить в заблуждение.

## Правила

- Прототип – одноразовый инструмент проверки. Не превращай его в продукт без переписывания.
- Одна версия – один вопрос. Меняй прототип между сессиями только если ошибка очевидна и мешает проверять остальное.
- Подписывай версию и дату.

## Анти-паттерны

- Прототип всего продукта сразу.
- Идеальный дизайн до проверки сценария.
- Тестовые данные «Иванов Иван, Отдел 1».
