# План реализации

Цель – план, по которому исполнитель без контекста проекта (новый разработчик или ИИ-агент в чистой сессии) сделает работу маленькими шагами, каждый из которых проверяется.

## Вход

Согласованные требования (`requirements-spec`, прошедшие `spec-review`), существующий код, ограничения (стек, размещение, ИБ). Если требований нет или в них есть блокирующие `OPEN` – остановись и верни вопросы.

## Шаг 1. Изучи то, что есть

- Прочитай структуру проекта, ключевые модули, соглашения (именование, тесты, линтер), README и существующие решения (ADR).
- Найди, что уже реализовано похожего, – переиспользуй, а не дублируй.
- Запиши, что затронет изменение.

## Шаг 2. Технический дизайн (коротко)

```markdown
## Дизайн
Подход: …
Компоненты и их ответственность: …
Данные: новые сущности/поля, миграции
Интеграции: …
Безопасность: аутентификация, права, ПДн, секреты
Что не делаем (YAGNI): …

## Решения
- Решение: … | Альтернативы: … | Почему: … (значимое – в ADR, см. documentation)

## Риски
```

Принципы: самое простое решение, которое удовлетворяет требованиям; без «на будущее»; совместимость с текущим кодом важнее красоты.

## Шаг 3. Разбей на задачи

Каждая задача:
- занимает от нескольких минут до пары часов;
- даёт работающее состояние (проект собирается, тесты проходят);
- проверяется тестом или наблюдаемым результатом;
- указывает точные файлы.

Порядок: сначала то, что снимает главный технический риск; затем «ходячий скелет» сквозного сценария; затем наращивание.

## Формат задачи

```markdown
### Задача 3: Проверка остатка дней при создании заявки
Требования: FR-004, AC-07, BR-02
Файлы: src/leave/validation.py (изменить), tests/leave/test_validation.py (создать)

Шаги:
1. Написать тест: заявка на 10 дней при остатке 5 → ошибка «недостаточно дней» с остатком в сообщении.
2. Запустить тест – убедиться, что падает по ожидаемой причине.
3. Реализовать минимальную проверку.
4. Запустить тест – проходит. Запустить все тесты модуля.
5. Коммит: «leave: проверка остатка дней при создании заявки».

Готово, когда: тесты AC-07 проходят, остальные не сломаны.
```

## Шаг 4. Сквозные задачи

Не забудь в плане: миграции и откат, конфигурация и секреты, логирование и метрики, обработка ошибок внешних систем, тексты интерфейса, документация, проверка безопасности (`security-review`), приёмочная проверка по AC.

## Шаг 5. Проверь план

- Каждое требование покрыто хотя бы одной задачей; каждая задача ссылается на требование.
- Нет задачи «и всё остальное».
- Нет скрытых зависимостей между задачами.
- Понятно, как проверить каждую задачу.

## Правила исполнения (для того, кто пойдёт по плану)

- Одна задача за раз. Не начинай следующую, пока не проверена текущая.
- Отклонился от плана – обнови план и скажи почему.
- Нашёл противоречие в требованиях – стоп и вопрос, а не догадка.
