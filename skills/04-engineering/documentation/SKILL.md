# Итоговая документация

Цель – человек, который не участвовал в проекте, сможет пользоваться, запустить, поддерживать и понять, почему сделано именно так.

## Четыре вида документации (Diátaxis)

| Вид | Вопрос читателя | Пример |
|---|---|---|
| Обучение | «Как начать?» | Первый запуск за 10 минут |
| Инструкция | «Как сделать X?» | Как добавить нового пользователя бота |
| Справка | «Что именно делает Y?» | Описание API, параметров конфигурации |
| Объяснение | «Почему так?» | Архитектура, ADR |

Не смешивай виды в одном тексте: инструкция не должна превращаться в лекцию.

## README репозитория

```markdown
# <Название>
Одно-два предложения: что это и для кого.

## Что умеет
## Быстрый старт
Требования, установка, настройка (.env.example), запуск – команды, которые можно скопировать.
## Конфигурация
| Переменная | Назначение | Пример | Обязательна |
## Как устроено (коротко, ссылка на подробности)
## Разработка
Тесты, линтер, ветки, как внести изменения.
## Развёртывание
## Ограничения и известные проблемы
## Лицензия и авторы
```

Проверь: команды из «Быстрого старта» реально работают на чистой машине.

## ADR – запись архитектурного решения

Одно значимое решение – один файл `docs/adr/NNNN-<название>.md`. Не переписывается после принятия: если решение меняется – новый ADR, ссылающийся на старый.

```markdown
# ADR-0003: Хранить черновики заявок на сервере, а не в браузере
Статус: принято | Дата | Участники

## Контекст
Что происходит, какие ограничения, почему нужно решение.
## Решение
Что выбрали.
## Альтернативы
| Вариант | Плюсы | Минусы |
## Последствия
Что станет проще, что сложнее, что нужно сделать.
```

## Инструкция пользователя

- По задачам пользователя, а не по экранам: «Как взять отпуск», «Как перенести отпуск».
- Шаги нумерованные, одно действие на шаг, результат после каждого важного шага.
- Скриншоты – только где без них не понять; подпиши, что на них важно.
- Раздел «Если что-то пошло не так» с частыми проблемами и куда обращаться.
- Лучшая инструкция – та, которая не нужна: если инструкция длинная, возможно, нужно менять интерфейс (`ux-review`).

## Руководство администратора и runbook

- Архитектура и зависимости, где что развёрнуто.
- Конфигурация, секреты (где хранятся, не сами значения), доступы.
- Мониторинг: какие метрики и алерты, что считается нормой.
- Типовые инциденты: симптом → диагностика → действия → кого звать.
- Резервное копирование и восстановление, откат релиза.
- Регламентные операции (обновление справочников, ротация ключей).

## Описание API

- Предпочтительно машиночитаемо (OpenAPI), с примерами запросов и ответов.
- Для каждой операции: назначение, права, вход, ответ при успехе, все ответы при ошибках, идемпотентность, ограничения.

## Заметки о выпуске

```markdown
## Версия 1.4 – <дата>
### Новое
- Руководители видят график отпусков команды (для кого, зачем)
### Исправлено
### Изменения, требующие действий
### Известные ограничения
```

Пиши для пользователя, а не для разработчика: «теперь видно…», а не «добавлен эндпоинт…».

## Проверка документации

- Документация соответствует текущему коду и поведению (не версии полугодовой давности).
- Нет секретов, внутренних адресов и реальных ПДн.
- Кто-то, кто не писал, прошёл по инструкции и у него получилось.
