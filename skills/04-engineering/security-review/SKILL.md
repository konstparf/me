# Проверка безопасности

Цель – найти уязвимости, которые реально можно использовать, и не утопить команду в теоретических замечаниях.

## Правила отбора находок

- Сообщай только то, где видишь реальный путь эксплуатации. Уверенность ниже ~80% – в раздел «Проверить», а не в находки.
- Для каждой находки: где, как воспользоваться (шаги), что получит атакующий, как исправить.
- Не дублируй замечания стиля и общего качества – это `code-review`.

## Шаг 1. Модель угроз (коротко)

- **Что защищаем:** данные (ПДн сотрудников, зарплаты, оценки, медицинские сведения), действия (согласование, изменение кадровых данных), доступы (токены, интеграции).
- **Кто может атаковать:** внешний злоумышленник; сотрудник, который хочет увидеть чужое (зарплату коллеги); скомпрометированная учётная запись; вредоносная зависимость; для LLM – автор текста, который попадёт в промпт.
- **Границы доверия:** где данные приходят извне – браузер, бот, внешний API, загрузка файла, ответ модели.

## Шаг 2. Проверка по OWASP Top 10:2025

| # | Категория | Что проверить в нашем коде |
|---|---|---|
| A01 | Нарушение контроля доступа | Проверка прав на сервере на **каждое** действие и объект. Подстановка чужого ID в URL/запрос (IDOR). Руководитель видит только свою команду. Замещение и делегирование ограничены по сроку и объёму. SSRF – запросы по URL, пришедшему от пользователя |
| A02 | Ошибки конфигурации | Отладочный режим выключен, лишние порты и эндпоинты закрыты, заголовки безопасности, CORS не `*`, стандартные пароли сменены |
| A03 | Цепочка поставок ПО | Lock-файл, известные уязвимости в зависимостях, происхождение пакетов, права CI/CD, проверка образов |
| A04 | Криптография | TLS везде, хранение паролей – только медленные хеши (argon2, bcrypt), нет самодельной криптографии, ключи не в коде |
| A05 | Внедрение | Параметризованные запросы к БД, экранирование вывода (XSS), нет сборки shell-команд из ввода, безопасный разбор XML/шаблонов |
| A06 | Небезопасный дизайн | Ограничения бизнес-логики (лимиты, необратимые действия с подтверждением), защита от перебора, разделение ролей |
| A07 | Аутентификация | Корпоративный SSO, сессии с истечением и отзывом, защита от перебора, безопасное восстановление доступа |
| A08 | Целостность данных и ПО | Проверка подписей обновлений, безопасная десериализация, защита от подмены данных из интеграций |
| A09 | Журналирование и оповещения | Логируются входы, отказы в доступе, изменения прав и кадровых данных, доступ к ПДн. В логах нет паролей, токенов и лишних ПДн. Есть оповещения об аномалиях |
| A10 | Обработка исключительных ситуаций | Ошибки не раскрывают внутренности (стеки, SQL), при сбое система закрывает доступ, а не открывает (fail closed), нет полусостояний |

## Шаг 3. Персональные данные (152-ФЗ и внутренние требования)

- Перечень ПДн, которые обрабатываем, и цель обработки. Не собираем лишнего.
- Доступ по ролям и принципу минимальных прав; журнал доступа к ПДн.
- Особые категории (здоровье и др.) – отдельные требования и согласия.
- Срок хранения и удаление.
- Где физически хранятся данные: локализация баз с ПДн граждан РФ на территории РФ; внешние облака и зарубежные API (в том числе LLM) – только с обезличенными данными или по согласованию с ИБ и юристами.
- Обезличивание в тестовых средах, выгрузках, аналитике, логах.

## Шаг 4. Секреты

- Поиск секретов в коде и истории git (gitleaks, trufflehog или аналог).
- Токены ботов, ключи API, пароли БД – в переменных окружения или хранилище секретов.
- Минимальные права у сервисных учётных записей и токенов.
- Утёкший секрет – отозвать и заменить.

## Шаг 5. LLM-приложения и боты (OWASP Top 10 для LLM)

- **Внедрение инструкций (prompt injection):** текст от пользователя, из документов, писем, веб-страниц может содержать команды для модели. Модель не должна иметь права на действия, которые опасны при таком захвате; критичные действия – с подтверждением человека.
- **Утечка данных:** что модель видит в контексте, то она может пересказать. Не клади в промпт данные, которые этот пользователь не должен видеть. Системный промпт не считать секретом.
- **Небезопасная обработка ответа:** ответ модели – недоверенный ввод. Не исполнять как код, не вставлять в SQL/HTML без экранирования.
- **Избыточные полномочия агента:** минимальный набор инструментов и прав.
- **Расход ресурсов:** лимиты на длину запросов, число запросов на пользователя, бюджет.
- **Доступ к боту:** белый список пользователей, проверка на каждом сообщении.
- **Передача данных провайдеру модели:** какие данные уходят, где обрабатываются, соответствует ли требованиям компании.

## Шаг 6. Автоматические проверки (если есть доступ к коду)

- SAST: Semgrep, Bandit (Python), ESLint security-плагины.
- Зависимости: `pip-audit`, `npm audit`, OSV-Scanner, Dependabot.
- Секреты: gitleaks.
- Контейнеры: Trivy.

Автоматика – дополнение, а не замена ручной проверки логики доступа.

## Формат отчёта

```markdown
# Проверка безопасности: <что>, <дата>

## Итог
Можно выпускать / после исправления критичных / нельзя.

## Находки
### [Высокий] Просмотр чужих заявок через подстановку ID
Где: `GET /api/leave/{id}` (src/leave/api.py:57)
Как воспользоваться: авторизованный сотрудник меняет id в запросе и получает заявку другого сотрудника с диагнозом в комментарии.
Последствия: утечка ПДн, в том числе особой категории.
Исправление: проверять, что заявка принадлежит пользователю или его подчинённому; вынести проверку в общий слой.
Уверенность: высокая.

## Проверить дополнительно (уверенность ниже)
## Что проверено и не найдено проблем
## Автоматические проверки: что запускалось, результат
```

Серьёзность: высокий – можно получить чужие данные или права без особых условий; средний – нужны особые условия; низкий – ограниченный ущерб.
