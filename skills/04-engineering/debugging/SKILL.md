# Систематическая отладка

Главное правило: **не исправляй, пока не нашёл причину.** Исправление симптома создаёт новые ошибки и прячет настоящую.

## Фаза 1. Расследование причины

1. **Прочитай ошибку полностью** – сообщение, стек, номер строки, код ошибки. Часто ответ уже там.
2. **Воспроизведи стабильно.** Точные шаги, данные, окружение. Не воспроизводится – собирай больше данных, а не гадай.
3. **Что изменилось?** Последние коммиты, зависимости, конфигурация, данные, окружение. `git log`, `git diff`, `git bisect`, если неясно, когда сломалось.
4. **Собери доказательства на границах.** В системе из нескольких компонентов (бот → API → БД → внешний сервис) добавь логирование на входе и выходе каждого и найди, где данные становятся неправильными.
5. **Проследи плохое значение назад** – откуда оно пришло, кто его передал, где исходный источник. Исправлять нужно в источнике.

## Фаза 2. Сравнение с работающим

- Найди похожий код, который работает. Чем отличается?
- Если используешь библиотеку или API – прочитай документацию или пример полностью, а не по диагонали.
- Перечисли все различия, даже мелкие. Не отбрасывай «это не может влиять».

## Фаза 3. Гипотеза и проверка

- Сформулируй одну гипотезу: «Причина – X, потому что Y».
- Проверь минимальным изменением, по одной переменной за раз.
- Подтвердилась – фаза 4. Нет – новая гипотеза, а не ещё одно исправление поверх.
- Не знаешь – скажи «не знаю» и собери больше данных.

## Фаза 4. Исправление

1. Напиши тест, который воспроизводит ошибку и падает.
2. Исправь причину – одно изменение.
3. Тест проходит, остальные не сломаны.
4. Проверь исходный сценарий вручную.

## Стоп-сигналы

Если поймал себя на мысли:
- «Быстро поправлю, потом разберусь»;
- «Попробую поменять X и посмотрю»;
- «Сделаю несколько изменений сразу»;
- «Наверное, дело в…» без проверки;
- «Ещё одна попытка» после двух неудачных –

вернись к фазе 1.

**Три неудачных исправления подряд** – сигнал, что проблема не в коде, а в подходе или архитектуре. Остановись и обсуди с человеком, прежде чем пробовать четвёртое.

## Отчёт об исправлении

```markdown
## Ошибка: <кратко>
Симптом: …
Как воспроизвести: …
Корневая причина: …
Почему не поймали раньше: …
Исправление: …
Тест: …
Похожие места, где может быть то же: …
```

Последний пункт важен: та же ошибка часто живёт в соседнем коде.
