# Маршрутизатор скиллов

Цель – подобрать минимальный набор скиллов под задачу и правильный порядок.

## Шаг 1. Определи, что на входе

| На входе | Стадия | Начни с |
|---|---|---|
| Идея, просьба, «давайте сделаем» | Разбор | `idea-triage` |
| Нужно разобраться в теме, найти аналоги | Исследование | `desk-research` → `fact-check` |
| Вопросы к пользователям, нужно понять, как работают сейчас | Исследование | `user-interviews` → `research-synthesis` |
| Нужны числа, масштаб, базовая линия | Исследование | `data-analysis` |
| Понятна боль, нужно сформулировать | Формулировка | `problem-statement` → `jtbd` |
| Есть идея решения, неясно, сработает ли | Формулировка | `hypotheses` |
| Много идей и задач, что первым | Формулировка | `prioritization` |
| Процесс запутан, много участников | Формулировка | `process-modeling` |
| Нужно увидеть опыт пользователя целиком | UX | `cjm` → `service-blueprint` |
| Нужна структура сервиса, экраны, навигация | UX | `user-flows-ia` |
| Нужно показать или проверить решение | UX | `prototyping` → `usability-testing` |
| Нужно нарисовать или улучшить интерфейс | UX | `ui-design` + `ux-writing` |
| CRM, реестр, админка, очередь согласований, рабочее место HR | UX | `complex-ui` + `ui-design` + `ux-writing` |
| Нужна быстрая оценка интерфейса | UX | `ux-review` |
| Решение выбрано, нужно передать в разработку | Требования | `requirements-spec` → `user-stories` → `spec-review` |
| Требования согласованы, пора писать код | Разработка | `implementation-plan` → `coding-workflow` |
| Ошибка, падает, работает странно | Разработка | `debugging` |
| Изменения готовы к слиянию | Разработка | `code-review` + `security-review` |
| Нужно проверить качество | Разработка | `testing` |
| Фича или проект завершены | Разработка | `documentation` |
| Нужно обосновать деньгами | Обоснование | `business-case` |
| Нужно согласование руководства | Обоснование | `decision-defense` |
| Сервис готов к выпуску или им не пользуются | Внедрение | `launch-and-adoption` |
| Нужен новый скилл | Мета | `skill-writing` |

`working-principles` загружается всегда.

## Шаг 2. Не перепрыгивай стадии

Если задача пришла на поздней стадии («напиши ТЗ на бот»), но ранние вопросы не закрыты (неясно, есть ли потребность), – скажи об этом, предложи короткий разбор (`idea-triage`) и спроси, делать ли его или идти дальше на допущениях. Если человек выбирает идти дальше – все непроверенные вещи помечай как `ДОПУЩЕНИЕ`.

## Шаг 3. Подбери глубину

- Маленькая задача, легко переделать – один-два скилла, коротко.
- Дорогая или необратимая задача – полная цепочка с вычиткой (`spec-review`, `security-review`, `code-review` отдельным проверяющим).

## Полный конвейер (для крупной инициативы)

```
idea-triage
 → desk-research / user-interviews / data-analysis → fact-check → research-synthesis
 → problem-statement → jtbd → process-modeling
 → cjm → service-blueprint
 → hypotheses → prioritization → business-case
 → user-flows-ia → prototyping → ux-writing / ui-design / complex-ui → ux-review → usability-testing
 → decision-defense (согласование)
 → requirements-spec → user-stories → spec-review
 → implementation-plan → coding-workflow ⇄ debugging → testing → code-review → security-review
 → documentation → launch-and-adoption
```

Это карта, а не обязательный маршрут: большинство задач проходит 3–5 шагов.

## Для своего агента

Маршрутизатор можно встроить в бота: первым шагом модель получает только этот файл и запрос, отвечает списком скиллов, затем бот подгружает выбранные `SKILL.md` в контекст. Так контекст остаётся маленьким, а инструкции – точными.
